# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This repo has two parts: a frontend (root) and a backend API (`server/`), deployed as separate services in the same Railway project but wired together at runtime — the frontend has no local persistence of its own, it's a thin client over the API's shared, ELO-rated leaderboard. Multiple people pointed at the same API/database see and add to the same players and matches.

## Deployment (Railway)

Everything lives in one Railway project (`tennis_tracker`, linked locally via `railway link`), as three services:

- **`Postgres`** — managed Postgres, public networking disabled by default. To connect from a laptop, use `railway connect Postgres --tunnel-only` (opens a local encrypted tunnel, prints a one-off `localhost` connection string+password) rather than enabling the database's public URL.
- **`tennis_tracker`** — the frontend. Auto-connected to the GitHub repo at the **root directory** (no override needed, since the frontend lives at repo root); Railway auto-detected it as a static Vite site and serves the `dist/` build via Caddy. **Auto-deploys on push to `main`** via a Railway deployment trigger (created 2026-09-24 with the `deploymentTriggerCreate` GraphQL mutation through `railway api`). For a long time it silently did *not* deploy: the service had a repo source but no trigger, because Railway's GitHub app didn't have access to the repo ("no one in the project has access to it"); fixed by granting the Railway GitHub app access to the repo (GitHub → Settings → Applications → Railway → Configure) and re-running the mutation. If pushes stop deploying again, check `railway deployment list --service tennis_tracker` and that the trigger still exists (`deploymentTriggers` query); manual fallback is `railway redeploy --service tennis_tracker --from-source --yes`. Env var `VITE_API_URL` points at the `api` service's public domain — since Vite bakes `VITE_*` vars in at *build* time, changing this variable requires a rebuild, not just a restart: `railway redeploy --service tennis_tracker --from-source --yes` (plain `redeploy` without `--from-source` replays the old build artifact and won't pick up the new value).
- **`api`** — the backend (`server/`). Created as an empty service (`railway add --service api`) rather than connected to the GitHub repo, because this repo is a monorepo and connecting the whole repo would build the frontend's root `package.json` instead of `server/`'s. Deployed by running `railway up server --path-as-root --service api` from the repo root (plain `railway up` from inside `server/` still uploads the whole repo — `--path-as-root` is what scopes the build to that subdirectory). **Does not auto-deploy on push** — after backend changes, redeploy manually with that same command. Its `DATABASE_URL` is set to `${{Postgres.DATABASE_URL}}` (a Railway variable reference), which resolves to the *internal* `postgres.railway.internal` address — the deployed API talks to Postgres over Railway's private network, never the public internet.

Both `tennis_tracker` and `api` have public domains generated via `railway domain --service <name>` (`*.up.railway.app`). A custom domain (e.g. from Namecheap) would get pointed at the frontend's Railway domain via CNAME — not yet set up.

## Commands

Frontend (repo root):
- `npm run dev` — start the Vite dev server (default port 5173)
- `npm run build` — typecheck (`tsc -b`) then production build to `dist/`
- `npm run lint` — run oxlint over the codebase
- `npm run preview` — serve the production build locally

Backend (`server/`):
- `npm run dev` — start the API with hot reload (`tsx watch`), default port 3001
- `npm run migrate` — run `src/schema.sql` against `DATABASE_URL` to create/update tables
- `npm run build` / `npm start` — compile to `dist/` and run the compiled server

There is no test runner configured for either part yet.

## Architecture

### Frontend (mobile-first React SPA)

Vite + React 19 + TypeScript. Talks to the backend over HTTP; holds no data of its own beyond in-flight component state.

- **`src/lib/api.ts`**: the only place that knows the API's base URL (`VITE_API_URL`, defaulting to `http://localhost:3001` for local dev) and endpoint shapes. `request()` throws on non-2xx responses using the API's `{error}` JSON body, so callers can just `try/catch`, and returns `undefined` for 204 responses.
- **State**: `App.tsx` is the single source of truth — it holds `players` and `matches` in state, fetches both on mount, and calls `api.createPlayer`/`api.createMatch` then **refetches both lists** on any mutation (rather than optimistically patching local state), so the UI always reflects what the server actually persisted. No global store or context.
- **Domain model**: matches are between two registered players (`playerAId`/`playerBId`), not a free-text opponent — this mirrors the backend's model exactly (see below), there's no separate frontend-only `Match` type anymore.
- **Derived stats**: `src/lib/records.ts`'s `computeStandings(players, matches)` builds each player's standing (W/L, win %, current streak, ELO change from their last match) by scanning the matches array, sorted by ELO — kept as a pure function rather than stored state so it can't drift from the source data. The last-match ELO delta is derived from consecutive `*_elo_after` values (baseline 1200), not stored.
- **Logo** (`src/assets/logo.png`): the user's own hand-drawn artwork (racket with a yellow grip, ball, two trees; an earlier version also had three black birds, dropped at the user's request because they read as specks at badge size), not AI-generated or redrawn — cropped from their original file to its content bounding box and had its flat white background keyed to transparent (purely mechanical edits; no drawn pixel was altered/recolored). The racket *and* the trees are drawn in `#006633`, which is *exactly* `--color-court` — rendering them directly on the header would make them invisible (identical color, contrast ratio 1.0; only the yellow ball and grip would show). So the logo sits in a small white circular badge (`bg-white rounded-full`) in the header instead of directly on the green — that badge is required for the racket/trees to be visible at all, don't remove it without giving them contrast some other way. The user has replaced this file several times (racket+ball → +birds+trees → birds removed) and may again; if so, redo both the crop and the transparency key the same way (bounding box of non-white pixels; white→transparent threshold ~250/255 per channel) rather than hand-editing, and re-check each drawn color's contrast against `--color-court` before assuming the white badge is still sufficient.
- **Brand palette** (`src/index.css`, Tailwind v4 `@theme`): `--color-court` (#006633, Wimbledon green — the dominant color, header/primary buttons/selected states) and `--color-ball` (#f2f65f, a tennis-ball yellow — a deliberately sparing accent, used only where it needs to pop: the floating `+ Match` button, the dark-mode "Edit" link; never as body text or a large fill, since it's too pale for contrast at that size). **No gradients** — the user considers them a tell for low-effort AI-generated design, so the hero and all buttons are flat fills; don't reintroduce one without asking.
- **Layout** (modelled on the Rankat app's league page; reference screenshots live in the gitignored `Inspiration/` folder — don't commit them, they're another app's artwork): a flat `bg-court` hero, a white rounded panel, and a fixed **bottom nav** (`BottomNav`) that switches between two pages — **League** and **Courts**. `App.tsx` holds `page` in plain state (no router, so the URL doesn't change and a refresh returns to League). The League page has a Standings/Matches segmented toggle and a floating **+ Match** button (bottom-right, hidden on the Courts page) that opens the match form in a bottom `Sheet`; adding/removing players is behind "Manage members" (also a `Sheet`). No copyrighted Rankat art is used. Not built (no data model for them yet): seasons, multiple leagues/join codes, tournaments.
- **Player profiles**: tapping a Standings row, or a player's name in the Matches list or in another profile's history, opens that player's profile — a view *within* the League page (`profileId` in `App.tsx`; the hero swaps to the player's initial, rank and ELO with a "‹ League" back button). It pushes one `history` entry (hopping profile→profile *replaces* it), so the phone's back gesture returns to the list instead of leaving the app; switching bottom-nav pages closes it. `PlayerProfile` shows a `RatingChart` (hand-rolled SVG, one point per match in rating/`id` order from 1200, a readout row above it instead of a floating tooltip so a finger never covers the value while scrubbing), W/D/L tiles, highlights (highest rating, best win by opponent's pre-match ELO, best win streak) and a chess.com-style history (result badge, opponent with their pre-match ELO, score, ELO change). All derived client-side by `computeProfile` in `records.ts`; pre-match ratings aren't stored, so it recovers them by walking all matches in `id` order — the same order `replayRatings` applies them — so the per-match deltas are exact.
- **Courts page**: `CourtsTable` renders `src/data/courts.ts` (`PARKS`, generated from `PDX_Courts.xlsx` and later updated from `Tennis Courts - PDX Courts.csv`, which added Gabriel Park; its drive-time and Google Maps columns are unused) — static data bundled into the app, not in the database or API. It has a search box, click-to-sort Park/Courts/Quality headers (Quality is the user's own letter grade from the sheet (A best … F worst, optional +/-; `gradeRank` in `courts.ts` orders them), `null` = not graded — 26 of 32 parks so far — shown as "–" and always sorted last in either direction; Courts and Quality default to best-first), and a footer with the park count and total courts for the current filter. To change the list, edit `courts.ts` directly (the source listed Fernhill Park twice with 2 courts; it's listed once). Each park also has `lat`/`lng` of its *tennis courts* (derived from OpenStreetMap tennis features nearest each park's pin, not the park centroid — e.g. Washington Park's courts are far from its center).
- **Find courts near you** (top of the Courts page): the visitor types an address or taps "Use my location", and the table gains a **Drive** column sorted closest-first. All of this runs in the visitor's browser (`src/lib/geo.ts`) against free, keyless public services — **not** through our API/server, so an address never touches our infrastructure: address → coordinates via OpenStreetMap **Nominatim** (limited to a Portland-metro `viewbox`; free-use policy asks for light use), and real driving minutes via the **OSRM public demo router** (one `table` request covers every park). Both are best-effort with no uptime guarantee; if OSRM fails or returns bad data, `getDriveTimes` falls back to a straight-line estimate (distance × 1.3 ÷ 35 km/h) and the UI shows "≈" plus a warning. No live-traffic data. Gotcha when testing from Node: Nominatim returns 403 to Node's default User-Agent, while real browsers (which send their own User-Agent/Referer) are fine — add browser-style headers in test harnesses. The user's own CSV drive times are from one fixed origin and are not used. Swapping to Google Maps (traffic-aware) would need their API key/billing.
- **Components** (`src/components/`): `BottomNav`, `CourtsTable`, `Standings` (rows are buttons that open the player's profile; 👑 for #1, 🔥/🗑️ streak badge at 3+ in a row, ▲/▼ last-match ELO change), `Sheet` (generic bottom sheet, closes on backdrop/Escape), `MembersPanel` (add form + member list with an inline two-step Remove → Confirm that states how many matches will be deleted; lives in the "Manage members" `Sheet`), `AddPlayerForm`, `MatchForm` (doubles as the edit form when given `initial` + the passcode props — the passcode field and a "Delete match" button, with a red confirm box, appear only when editing; a Set/Tiebreak toggle at the top picks `MatchType`, for a set, the score inputs are replaced with `GamePicker` — a row of tap-to-pick buttons for 0-8 (the 8-game cap exists specifically so this fixed button range is always valid), since typing on a number pad for a 9-value range is more friction than it needs to be; a tiebreak keeps the plain number input (points aren't capped) — client-side-validated to reject a tied tiebreak or a set above 8 games before either reaches the server; **the `<form>` has `noValidate`**, without which the browser's own number-input constraint validation from that `max` attribute silently blocks submission before React's `onSubmit` ever runs, so the custom red-text error never shows — a real bug caught in testing, don't remove `noValidate` when touching this form; players are picked by tapping two name chips — the first tap is player A, the second is B, a third tap drops the earliest pick — then a games/points box appears for each, plus an optional Park dropdown built from `PARKS` in `src/data/courts.ts`; shows a placeholder when fewer than 2 players exist; defaults the dropdowns to the first two players by deriving from state during render rather than an effect), `MatchList` (player names open their profile; shows a small "Tiebreak" badge on tiebreak rows; each match has an Edit button that opens `MatchForm` in an "Edit match" `Sheet`; bolds the winner, shows post-match ELO for both). All presentational; `App.tsx` owns data, the active tab, and which sheet is open, and closes the sheet after a successful submit.
- **Styling**: Tailwind CSS v4 via the `@tailwindcss/vite` plugin (not the old PostCSS/config-file setup — there is no `tailwind.config.js`). Global styles/import live in `src/index.css`. Layout is constrained to `max-w-md` and built mobile-first since the app is meant to be used courtside on a phone; dark mode is handled via Tailwind `dark:` classes.
- Dates are stored/sent as `YYYY-MM-DD` strings (from `<input type="date">`); when displaying a date that came back from the API, use `.slice(0, 10)` rather than `new Date(...).toLocaleDateString()` — the API returns a UTC-midnight timestamp for `DATE` columns, and `toLocaleDateString()` can roll it back a day depending on the viewer's timezone.

### Backend (`server/`) — Express + Postgres API

Supports multiple people logging matches against a shared, ELO-rated leaderboard. Deployed independently of the frontend (e.g. Railway for the API + Postgres, Vercel for the static frontend) — locally they run as separate dev servers (frontend on 5173, API on 3001), connected only by `VITE_API_URL`.

- **`src/db.ts`**: a `pg` `Pool`, configured from `DATABASE_URL` if set, else discrete `PGHOST`/`PGPORT`/`PGUSER`/`PGPASSWORD`/`PGDATABASE` vars.
- **`src/schema.sql`**: two tables — `players` (name, `elo`, starts at 1200) and `matches`. **A "match" is a single set OR a single tiebreak** (`match_type`, `'set'` or `'tiebreak'`, CHECK-constrained, defaults to `'set'`) — always one standalone row of either kind, never a set containing a tiebreak. `score_a`/`score_b` are games (set) or points (tiebreak) each player won, `park` is an optional free-text park name (stored as text, so a park missing from `courts.ts` — e.g. "Gabriel Park" from the imported results — still displays; blank is stored as NULL), `winner_id` is nullable (NULL = drawn, equal games), plus each player's post-match ELO. There is deliberately no multi-set/match concept — the user found it too complicated. The file runs as one multi-statement query (`src/migrate.ts` does `pool.query(sql)`), which is what allows the `DO $$ … $$` block that upgrades an older `sets JSONB` table (keeps the first set as the score, then drops `sets`). Applied via `npm run migrate`, not a migration framework — schema changes mean editing `schema.sql` and re-running migrate; `CREATE TABLE IF NOT EXISTS` won't alter an existing table, so changes to existing tables are also written as idempotent `ALTER TABLE … IF NOT EXISTS`/`DROP … IF EXISTS` statements below the CREATEs. The schema file also ends with an idempotent one-off `UPDATE` that moved park names the results import had put in `notes` into `park` (exact matches on four park names only; safe to delete later). Run migrate against production *before* deploying API code that depends on the change.
- **`src/elo.ts`**: the single source of truth for scoring — used by `POST /api/matches`, `replayRatings`, and the import script's preview, so they can never disagree. `computeEloUpdate(ratingA, ratingB, scoreA, k)` is standard Elo (400-point scale, `K × (actual − expected)`, base K = 30) where `scoreA` is 1 (A won), 0.5 (draw) or 0 (A lost); draws behave as in chess. `scoreMatch(gamesA, gamesB, type)` returns `{scoreA, k}` for a `MatchType` of `'set'` or `'tiebreak'` — **a match is one standalone row, either a set or a tiebreak, never a set containing a tiebreak** (no nesting, by design). More points/games wins; equal is a draw at base K, except a tiebreak can never tie (rejected in `matchInput.ts`, never reaches here). Otherwise, a tiebreak's winning score is first converted to game-equivalents (`÷ 4`, since a game is roughly 4 points) and run through the **same** games-standard sets use (standard = 6, `±0.1` per game) — there's deliberately one shared yardstick, not two separate formulas, so a tiebreak only matches a full set's weight once its winner reaches 24 points (6 equivalent games). **Sets are clamped both ways (×0.7–×1.3)** — real sets cluster at 5–7 games so this rarely binds, it mainly guards a mistyped score (hence the 8-game hard cap on sets in `matchInput.ts`, below). **Tiebreaks are clamped only on the high end** (×1.3, guards a freak-long or mistyped breaker) — deliberately **no floor**, so a normal 7–13 point breaker scales down for real (K ranges roughly 17–22) instead of flattening at some arbitrary minimum; the low end is naturally self-limiting anyway (a 1-point "win" only reaches ×0.425, nothing near zero or negative). The margin below the loser's score is deliberately ignored for both types. Tune via the constants at the top of the file. No I/O — safe to unit test directly.
- **`src/index.ts`**: routes for `GET/POST /api/players` and `GET/POST /api/matches`. Posting a match (`{playedOn, playerAId, playerBId, scoreA, scoreB, type?, park?, notes?}`; scores must be whole numbers ≥ 0 and not both 0; `type` is `'set'` (default when omitted) or `'tiebreak'`; **a `'set'` score above 8 games is rejected outright** (sets can't realistically go higher — this exists specifically to catch a fat-fingered score before it distorts K)) computes the result server-side via `scoreMatch` (the frontend never sends a "who won" flag); a drawn match is stored as `winner_id = NULL` (rejected outright for `type: 'tiebreak'`, which can never tie), updates both players' ELO in a transaction (`BEGIN`/`COMMIT`/`ROLLBACK` via a checked-out client, not the pool directly), and returns both new ratings — note this POST response is camelCase and shaped differently from the GET list's snake_case rows; the frontend doesn't rely on the POST body, it always refetches. A catch-all Express error handler returns JSON `{error}` on 500 instead of Express's default HTML stack-trace page. Postgres unique-violation (`code === '23505'`) is caught explicitly on player creation and returned as a 409, not a crash.
- Query placeholders are Postgres-style (`$1, $2, …`), not MySQL's `?` — this project switched from MySQL to Postgres early on; if you see `?` placeholders or `mysql2` anywhere, it's stale.
- **Deleting players**: `DELETE /api/players/:id` runs in one transaction — it deletes the player's matches, deletes the player, then calls `replayRatings` (`src/ratings.ts`), which rebuilds **every** player's ELO and every match's `*_elo_after` by re-scoring each remaining match from its stored `score_a`/`score_b`/`match_type` with `scoreMatch`, in `id` order (the order ratings were originally applied, *not* `played_on` order) from 1200. That's required because ELO is a running total: later matches were computed on top of the deleted ones. Replay is idempotent, so removing a player with no matches leaves everyone's ratings unchanged. **Matches can be edited and deleted**: `PUT /api/matches/:id` takes the same body as create, updates the row (including players, date, park, notes; `winner_id` recomputed), then calls `replayRatings`; `DELETE /api/matches/:id` deletes the row then calls `replayRatings` (404 if it doesn't exist). A match keeps its rating-order position (its `id`) even if its date is edited. Any feature that removes or changes a match must call `replayRatings` inside its transaction. Validation for create and edit lives in one place, `src/matchInput.ts` (`parseMatchInput`, `winnerOf`).
- **Passcode**: removing a player (`DELETE /api/players/:id`) and editing or deleting a logged match (`PUT` / `DELETE /api/matches/:id`) require the shared passcode in the `x-admin-passcode` header, checked **server-side** by `requireAdminPasscode` (`src/adminAuth.ts`) against the `ADMIN_PASSCODE` env var (set it on the Railway `api` service; never commit it). **Creating a match and adding a player deliberately need no passcode.** Fails closed: if `ADMIN_PASSCODE` is unset those routes return 503. Comparison is constant-time (SHA-256 + `timingSafeEqual`); 5 wrong guesses from one IP lock that IP out for 15 minutes (429, in-memory so a server restart clears it; friends on the same Wi-Fi/carrier NAT share an IP; `trust proxy` is set to 1 so `req.ip` is the real client behind Railway). It's a shared passcode, not per-user accounts — anyone who knows it can do both actions. The frontend keeps the passcode only in `App.tsx` state (gone on refresh, cleared when the server says "wrong passcode"), so it's asked once per session.
- `players.deleted_at` is a leftover column from a short-lived soft-delete design and is unused (nothing reads or writes it); it's safe to drop.
- CORS is wide open (`cors()` with no options) since this is a small personal-project API with no auth yet — fine for now, worth tightening if this ever handles real user data beyond a friend group.
